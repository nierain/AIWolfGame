## 修复：CLI 超时"假生效"，面板连同请求锁一起冻死

重启面板后第 2 夜一直不动，rain 问"还在聊天还是卡死了"。查出来的是一条**引擎外**的冻结：

**症状**：`panel_game.py` 的 `/api/state` 一直返回 `stale: true`（说明 `LOCK` 被占），
POST 任意动作一律超时；`state` 文件 mtime 十几分钟不变；**但面板进程一个子进程都没有**。

**根因（进程树实证）**：`CodexCLIProvider` 用 `subprocess.run(..., timeout=180)`。
Windows 上它超时后**只杀直接子进程**，紧接着还会再调一次 `communicate()` 想把管道读干净。
npm 的 `codex.cmd` 是个包装器，链是 `cmd.exe → node.exe → codex.exe`；超时杀掉 `cmd.exe` 后，
**node 与 codex.exe 变成孤儿却仍攥着继承来的 stdout/stderr 管道句柄**，那次 drain 就永久阻塞。
证据：`codex.exe 246560 ← node.exe 254812 ← PID 254484（已不存在）`，而面板 `254864` 无子进程、
`LOCK` 一直被占。杀掉那条孤儿链后一切恢复。

**修法**（`game/ai_providers.py`）：
- 新增 `_run_cli_with_timeout()`：自己 `Popen` + `communicate(timeout)`，超时走
  `_terminate_process_tree()`（Windows `taskkill /F /T`，POSIX `os.killpg`，并关掉我们这侧的管道），
  **杀完绝不再碰管道**；`subprocess.run` 在 `CodexCLIProvider` 和 `GenericCLIProvider` 里都不再使用。
- 新增 `_desktop_codex_candidates()`：优先用桌面端原生
  `%LOCALAPPDATA%\OpenAI\Codex\bin\*\codex.exe`，不再落到 npm 的 `codex.cmd`（少一层包装，
  也就少一层孤儿风险）。实测 provider 现在拿到的就是原生 exe。
- 回归测试 `test_cli_timeout_aborts_the_whole_process_tree`：造一个"自己再 fork 一层"的桩，
  断言超时能返回、且孙子进程被一起清掉。

**教训（差点写错结论）**：我第一版诊断脚本里 FAIL 分支的 `print` 没加 `flush=True`，
进程被 SIGTERM 时输出被缓冲区丢掉，于是误判成"75 秒超时完全没生效"。
**子进程里打印必须 flush**，否则会把丢失的输出当成结论。

**仍未解决**：修好后实测 Codex 调用**现在很慢/不返回**（连续两次在 180 秒内没结果，
面板返回 `HTTP 400 Codex 玩家思考超过 180 秒，请重试。`）。所以现在的瓶颈不再是我们的代码，
而是 Codex 后端本身（也可能是我短时间内并发打了好几次调用导致账号侧排队）。
处理方式：面板改用 `--cli-timeout 600` 重启（`启动狼人杀.bat` 没带这个参数，默认仍是 180）。

- 真人出局后要替某个 AI 座位行动，直接用模块级函数（`_wolf_explode`）或 `engine._apply`，
